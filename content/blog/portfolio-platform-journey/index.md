> 이 포트폴리오 사이트를 **왜·어떻게** 만들게 됐는지에 대한 회고다. 결론(Hugo Blox)만 보면 한 줄이지만, 거기 도달하기까지 열흘이 걸렸고 그 사이의 시행착오가 사실 더 쓸 만한 기록이라고 생각해서 따로 정리한다.

## 시작은 "한꺼번에 말고 조금씩"이었다

포트폴리오를 만들겠다고 마음먹었을 때 머릿속 그림은 단순했다. 이력서 한 장에 다 안 들어가는 프로젝트의 **맥락과 과정**을 담을 공간, 그리고 한 번에 완성하는 게 아니라 그때그때 **조금씩 점진적으로 업데이트**할 수 있는 구조. 처음엔 Notion으로 해봤다.

문제는 **자유도**였다. "프로젝트 카드 목록 → 클릭하면 상세"처럼 내가 원하는 레이아웃을 Notion에서는 자유롭게 못 만들었다. 그렇다고 사이트를 바닥부터 직접 코딩하자니 그건 그것대로 부담이었다. 내 조건을 정리하면 이랬다.

- AI 도구로 **점진적으로 업데이트**하고 싶다
- 레이아웃 **자유도**는 어느 정도 필요하다
- 그렇다고 프론트엔드를 처음부터 짜는 **고부담**은 피하고 싶다

이 세 조건이 가리키는 답은 결국 "콘텐츠는 Markdown으로 쓰고, git에 push하면 자동 배포되는" 구조였다. 그래서 Hugo / Astro / Webflow / Jekyll / Next.js를 비교했고, **Hugo + GitHub Pages** 조합이 1순위로 올라왔다. (이때 "정적 사이트가 정확히 뭔지"도 같이 공부했는데, 핵심은 JavaScript 유무가 아니라 *서버가 요청마다 HTML을 새로 만드느냐* 였다. 정적이어도 JS는 잘 돈다.)

곁가지 하나. 애초에 "실시간 업데이트 수단"으로 **openclaw**라는 걸 떠올렸었는데, 알고 보니 이건 포트폴리오 빌더가 아니라 메신저(WhatsApp/Telegram) 기반의 셀프호스트 AI 에이전트 플랫폼이었다. 보안 부담도 큰 편이라(노출된 인스턴스 상당수가 인증 우회 취약점을 안고 있다는 보고도 있었다) 결국 후보에서 빠졌다. 점진 업데이트는 openclaw가 아니라 **그냥 Markdown을 편집하고 git push 하는 흐름**으로 자연스럽게 수렴했다.

## 그리고 테마 하나에서 열흘을 잃었다

방향은 잡혔다. Hugo로 가자. 개발자 포트폴리오용으로 좋아 보이는 테마도 찾았다 — 이름이 `hugo-theme-developer-portfolio` 비슷한, "developer portfolio"를 표방하는 그것. `hugo new site`로 사이트 골격까진 만들었다. 여기까진 순조로웠다.

막힌 건 그다음이었다. 일반적인 Hugo 테마는 `themes/` 폴더에 넣고 설정에 `theme = "..."` 한 줄 적으면 끝이다. 그런데 이 테마는 **아무리 그렇게 해도 적용이 안 됐다.**

### 증상 → 원인 → 해결

**증상.** 테마를 `themes/`에 넣고 `theme` 설정을 줘도 레이아웃이 전혀 먹지 않았다. 빈 사이트만 나왔다.

**원인.** 리포 안을 뜯어보니 이상했다. 일반 테마라면 당연히 있어야 할 `layouts/`·`archetypes/`·`theme.toml`이 **없고**, 대신 `go.mod`만 덩그러니 있었다. 이게 결정적 단서였다.

여기서 깨달은 게 이 여정 전체의 핵심이다. **이름에 "theme"이 들어가 있어도, 그건 테마가 아니었다.**

- `dev-portfolio`는 **site starter**(완성된 사이트의 껍데기)다. `content/`·`data/`·`config/`만 들고 있고, 정작 레이아웃은 자기가 안 가진다.
- 진짜 엔진은 따로 있다. **`HugoBlox/kit`** 이라는 리포가 `modules/`·`templates/`를 들고 있는 본체다. (Hugo 테마 디렉터리에는 "Hugo Blox - Tailwind"로 등록돼 있고, 옛 Wowchemy / Hugo Academic이 리브랜딩된 것이다.)
- 둘은 부모-자식 관계다. starter가 **Hugo Modules 메커니즘으로 kit을 원격에서 끌어와** 빌드할 때 레이아웃을 합성한다.

즉 이건 "테마를 끼우는" 물건이 아니라 **"이 리포 자체를 시작점으로 통째로 클론하는"** 물건이었다. `Use this template`을 누르거나 Hugo Blox CLI로 시작해야 하는 거였다.

**해결.** 테마처럼 쓰려는 시도를 포기하고, dev-portfolio 리포를 통째로 프로젝트 시작점으로 삼았다. 이게 왜 그렇게 동작하는지는 Hugo의 **Hugo Modules** 때문이다 — 콘텐츠·에셋·테마·설정을 git 레포로 공유하는 구조라, 테마가 Go 모듈로 들어온다. (그래서 테마 `.html`을 직접 고치면 업데이트와 충돌한다. "정적 파일만 만진다"는 내 운영 원칙이 여기서 나왔다.)

> 추천을 받는 것과, 그 도구가 *어떻게 동작하는지*를 이해하는 건 완전히 다른 일이다. 후자는 보통 한 번 막혀봐야 학습된다.

## 그럼 일반 테마를 쓰면 되지 않나 — "갈아끼우기"라는 환상

dev-portfolio가 site starter라는 걸 알고 나니, 오히려 반대 방향의 의문이 들었다. *그럼 차라리 평범한 Hugo 테마를 쓰면 안 되나?* 더 솔직히 말하면, 나는 테마를 여러 개 받아두고 **갈아끼우며 사이트를 다양하게 바꿔볼 수 있을 줄 알았다**. 워드프레스처럼 콘텐츠는 그대로 두고 테마만 바꾸면 디자인이 통째로 갈리는 그림을 상상한 것이다. 그게 가능하다면 굳이 까다로운 HugoBlox를 고집할 이유도 없었다.

그래서 직접 물어봤다. themes.gohugo.io의 portfolio 테마끼리 호환이 되나? 마크다운만 잘 써두면 테마를 바꿔도 그대로 적용되나? 레이아웃 표준 같은 게 있나?

답은 분명했다 — **호환되지 않는다**. 특히 portfolio 카테고리는 거의 전부.

### 증상 → 원인 → 해결

**증상.** "콘텐츠를 잘 만들어두면 테마는 나중에 갈아끼우면 되지"라는 가정 자체가 통하지 않았다.

**원인.** Hugo는 의외로 **콘텐츠 스키마 표준이 거의 없는** 시스템이다. 테마와 무관하게 보장되는 건 사실상 이 정도뿐이다.

- 본문 마크다운 자체
- 기본 front matter 키 (`title`·`date`·`draft`·`tags`·`summary` 등)
- 디렉터리 구조(page bundle 규칙)와 taxonomy

반대로 **테마마다 제각각이라 옮기면 깨지는 것들**이 하필 포트폴리오의 핵심이다 — 대표 이미지를 `featured_image`로 부를지 `cover.image`로 부를지, 기술 스택을 `tech_stack`으로 둘지 `tools`로 둘지, 데모 링크를 `demo_url`로 받을지 `links` 배열로 받을지, 경력 타임라인의 키 이름, 그 테마만의 커스텀 숏코드까지.

블로그 글은 본질이 **prose**(글) 라서 본문만 옮기면 대부분 살아남는다. 그런데 포트폴리오는 *구조화된 데이터*("이 프로젝트는 Django로 만들었고, 데모는 여기, 스크린샷 5장, 기간 2022.03–2022.09…")라서, A 테마용으로 잘 써둔 `index.md`를 B 테마에 떨어뜨리면 이미지 안 뜨고, 기술 스택 칩 안 그려지고, 링크 버튼이 사라진다. 본문 글만 남는다. 대략 이런 스펙트럼이었다.

| 옮길 때 살아남는 정도 | 경우 |
|---|---|
| 거의 100% | 순수 블로그 글(제목·날짜·본문·태그) |
| 70–80% | 표준 블로그 테마 간 이동(이미지 경로만 손봄) |
| 30–50% | 비슷한 portfolio 테마 간(본문은 살고 메타데이터는 다시) |
| 거의 0% | HugoBlox ↔ 일반 테마, 블록 기반 ↔ 블록 기반 |

그리고 하필 내가 눈여겨본 HugoBlox는 **블록 기반**이라 이 호환성 면에선 최악이었다. 홈을 `_index.md`에 "어떤 블록을 어떤 순서로 쌓을지"를 YAML로 선언하는 방식이라, 이 콘텐츠는 다른 테마로는 거의 0% 옮겨가지 않는다.

**해결**(이라기보다 받아들임). 정리하면 이렇다 — Hugo에서 **테마 선택은 사실상 "사이트를 다시 짓는" 결심에 가깝다**. 워드프레스처럼 갈아끼우는 시스템이 아니다. 그러니 "나중에 바꾸면 되지"가 아니라 **처음 한 번을 신중히** 고르는 게 맞고, 그게 나중에 마이그레이션하는 것보다 훨씬 싸다. "갈아끼우기" 환상은 여기서 접었다.

### 그래서 며칠을 더 고민했다

호환이 안 된다면 첫 선택이 곧 거의 영구 선택이다. 그래서 며칠을 더 비교했다. 진지한 후보는 셋이었다.

- **HugoBlox** — 회사가 운영해 유지보수가 가장 활발(★9.8k), 기능이 가장 풍부(블로그·다크모드·심지어 논문/citation), 블록으로 확장이 자유롭다. 단 자기 생태계 락인이 있다.
- **Toha** — 개발자 포트폴리오로 가장 균형 잡혔고, `themes/`에 submodule로 얹는 표준 방식이라 **락인이 거의 없다**. 데이터/콘텐츠 분리도 깔끔하다.
- **Hugo Profile** — 가벼운 개발자 포트폴리오 특화. 개인 메인테이너.

"나중에 옮길 자유"를 최우선에 둔다면 Toha가 정답에 가까웠다. 그럼에도 내가 HugoBlox를 고른 이유는, **개발자 포트폴리오 기능의 충실도와 확장성**(블록·콘텐츠 타입·docs 사이드바)을 더 높게 봤고, 회사가 운영하는 만큼 업데이트가 끊길 걱정이 적었기 때문이다. "다른 테마로 옮기는 건 거의 불가능하다"는 비용은 **알고서 받아들였다**.

## 설치 지옥 — pnpm, Go, 그리고 OneDrive

작동 모델을 이해했다고 끝이 아니었다. Hugo Blox는 표준 Hugo와 의존성·툴체인이 미묘하게 달라서, 환경 세팅에서 또 한 번 걸렸다. 세 가지였다.

| 함정 | 증상 | 해결 |
|---|---|---|
| pnpm 누락 | npm으로는 의존성 설치가 안 됨 | Hugo Blox는 **pnpm**을 요구 — 별도 설치 |
| Go 누락 | 모듈을 못 끌어옴 | Hugo Modules가 Go에 의존 — Windows에선 Scoop으로 `scoop install go` |
| OneDrive 경로 | pnpm이 크래시 (`exit 3221226505`) | 프로젝트를 **OneDrive 밖**으로 이동 |

앞의 둘은 "없으니 깔자"로 금방 끝났다. 진짜 악질은 세 번째였다.

### 증상 → 원인 → 해결

**증상.** 프로젝트가 OneDrive 동기화 폴더 안에 있었는데, pnpm을 돌리면 `exit 3221226505`로 죽었다. 이 코드는 16진수로 풀면 `STATUS_STACK_BUFFER_OVERRUN`이다. 이름만 보면 무슨 보안 익스플로잇 같지만 실제로는 환경 문제였다.

**원인.** **OneDrive의 백그라운드 동기화가 `node_modules` 조작과 충돌**한 것이었다. pnpm이 수많은 파일을 빠르게 쓰고 지우고 링크하는 동안 OneDrive가 같은 파일을 동기화하겠다고 달려드니, 그 경합이 크래시로 터졌다.

**해결.** 처음엔 잔머리를 썼다. 폴더는 OneDrive 안에 두고, junction(심볼릭 링크)으로 OneDrive 밖을 가리키게 해서 동기화만 피해보려 한 것이다. **안 됐다.** 링크로 우회해도 동기화 충돌 자체는 해결되지 않았다. 결국 답은 단순했다 — 프로젝트를 **OneDrive 바깥**(`E:\AI\` 아래)으로 아예 옮기는 것. 지금 이 포트폴리오와 작업 환경이 전부 `E:\AI\` 밑에 사는 이유가 바로 이거다.

## 정착, 그리고 다음 사람에게

결국 도착한 곳은 **Hugo Blox의 `dev-portfolio`** 였다. 돌이켜보면 이 조합은 사실상 **여정 첫날에 이미 추천받았던** 것이다. 그런데 그게 "왜 일반 테마처럼 안 써지는지"를 몸으로 이해하는 데 **열흘**이 걸렸다. 그 열흘의 간극이 이 글의 본체다.

후보였던 다른 것들을 왜 안 골랐는지도 정리해 둔다.

| 대안 | 안 간 이유 |
|---|---|
| Notion | 레이아웃 자유도 부족 (애초에 떠난 이유) |
| openclaw | 포트폴리오 빌더가 아닌 메신저 에이전트 + 보안 부담 |
| Astro | 디자인 자유도는 최상이지만 프론트 러닝커브·Node 의존 (콘텐츠가 Markdown이라 나중에 이주할 여지는 남겨둠) |
| Toha / Hugo Profile | Hugo Blox 대안으로 검토했으나, 개발자 포트폴리오 기능 충실도에서 Hugo Blox 채택 |

같은 길을 갈 다음 사람에게 남기는 팁 세 가지로 마무리한다.

1. **이름을 믿지 마라.** "theme"이라는 단어가 붙어 있어도 site starter일 수 있다. 리포에 `layouts/`·`theme.toml`이 없고 `go.mod`만 있으면 그건 "끼우는" 게 아니라 "통째로 시작점으로 삼는" 물건이다.
2. **OneDrive 안에서 `node_modules`를 돌리지 마라.** `exit 3221226505` / `STATUS_STACK_BUFFER_OVERRUN`을 보면 코드 잘못부터 의심하지 말고 경로부터 확인하라. 링크로 우회되지 않으니 그냥 OneDrive 밖으로 옮기는 게 답이다.
3. **막히는 건 손해가 아니다.** "테마를 수정하지 않는다"는 제약 아래에서 헤맨 덕분에, 오히려 블록·콘텐츠 타입·Hugo Modules 같은 메커니즘을 제대로 이해하게 됐다. 도구의 작동 모델을 이해하는 비용은 보통 막혀봐야 치러진다 — 그리고 그 비용은 다음 작업에서 회수된다.
